# 任务量化 Skill：用户反推 → 设计 → 调研纠错 → 复用开发 → 部署反推 → 优化交付 → 复盘

## 核心哲学

> 不做简单的任务清单。要做的是**从用户怎么用出发，反推出产品需要什么，再反推出怎么开发，最后生成可执行的任务地图**。
>
> 调研不是起点，纠错才是它的本质。设计先于调研，复用先于创造。规划就是任务本身。

## 自适应模式

根据需求复杂度自动选择模式：

| 模式 | 触发条件 | 执行的 Phase | 适用场景 |
|------|---------|-------------|---------|
| **简化模式** | 一句话能说清、单系统、≤3天工作量 | Phase 1 → 量化任务地图 → Phase 7 → 自检 | 写一个功能、修一个bug、做一个页面 |
| **完整模式** | 多系统、有依赖、>3天工作量 | Phase 1→2→3→4→5→6→7 → 自检 → 复盘 | 开发一个产品、搭建一个系统、组织一场活动 |

**判断规则：**
- 如果用户没有提供任何细节 → 简化模式
- 如果需求涉及 ≥2 个独立子系统 → 完整模式
- 如果用户说"详细拆解" → 完整模式
- 如果用户说"简单列一下" → 简化模式

## 工作流程

### Phase 1：需求解析（不急着列任务）

收到用户需求后，先做以下分析：

1. **一句话复述**：用你自己的话复述用户要做什么，确认理解正确
2. **维度拆解**：从以下维度分析需求
   - **对象**：要处理什么？（代码/文档/设计/数据/用户...）
   - **目标**：最终产出是什么？（功能/报告/页面/系统...）
   - **约束**：有什么限制？（时间/技术栈/资源/质量要求...）
   - **复杂度**：单步任务 / 多步有依赖 / 多步无依赖
   - **成功标准**：怎么算完成了？
3. **领域适配**：判断这是什么类型的任务，调整侧重点
   - **代码开发类：** 强调验收标准、测试覆盖、CI/CD
   - **产品设计类：** 强调用户旅程、可用性测试、A/B 测试
   - **运营活动类：** 强调时间节点、资源协调、效果评估
   - **研究分析类：** 强调数据源、分析方法、结论验证
4. **模糊点澄清**：如果需求中有模糊之处，最多追问 2 个问题

### Phase 2：用户旅程反推

**假设产品已经做好了，站在用户的角度，一步一步地想他怎么使用。**

不要想技术、想架构、想数据库——先想**用户**。

1. **场景还原**：用户会在什么场景下打开这个产品？
2. **第一步操作**：用户进来的第一件事是什么？
3. **核心路径**：用户达成目标的最短路径是什么？
4. **关键触点**：用户在哪些环节会产生情感波动？（惊喜/困惑/放弃）
5. **留存钩子**：用什么机制让用户下次还想回来？

**输出格式：**

`
## 用户旅程

用户场景：[用户在什么情况下会使用]

步骤1: [进入产品] → 期望：[快速看到核心价值] → 设计要点：[首屏即价值]
步骤2: [核心操作] → 期望：[流畅无阻碍] → 设计要点：[最少步骤完成目标]
步骤3: [获得反馈] → 期望：[即时确认] → 设计要点：[明确的完成感]
步骤4: [留存/转化] → 期望：[还想再来] → 设计要点：[钩子机制]

流失风险点：[用户可能在哪些步骤放弃]
`

### Phase 3：产品设计

**从用户旅程的每一步，反推这个环节应该怎么设计才能让体验最舒适、最大化绑定用户。**

1. **信息架构**：产品的内容结构怎么组织？
2. **交互设计**：每个页面的操作流程是什么？
3. **核心功能定义**：MVP 必须有什么，暂时不需要什么（P0/P1/P2 分级）
4. **用户绑定机制**：用什么设计让用户产生依赖？

**输出格式：**

`
## 产品设计方案

### 信息架构
[页面层级结构]

### 核心功能清单
- P0（必须有）：[功能列表]
- P1（应该有）：[功能列表]
- P2（可以有）：[功能列表]

### 用户绑定策略
[用什么机制让用户留下来]

### 关键交互流程
[核心路径的交互设计]
`

### Phase 4：调研纠错

**调研的本质是纠错。有了设计方案之后，调研才有价值——你知道该纠正什么了。**

1. **竞品分析**：类似的产品怎么做的？他们做对了什么、做错了什么？
2. **技术可行性验证**：设计方案里的关键技术点有没有坑？
3. **用户场景验证**：设计的产品流程覆盖了真实的用户场景吗？
4. **差异化定位**：我们和竞品的差异点在哪里？

**输出格式：**

`
## 调研纠错报告

### 竞品分析
| 竞品 | 优点 | 缺点 | 我们可以借鉴的 |
|------|------|------|---------------|

### 技术风险
| 技术点 | 风险等级 | 应对方案 |

### 设计修正
[基于调研结果，对设计方案做出的调整]
`

### Phase 5：复用优先开发

**开发前的黄金法则：先上 GitHub 找有没有相似模块，基于相似模块调整改动，改不动的再自己写。**

1. **GitHub 搜索**：找相似的开源项目/模块/组件
2. **评估复用度**：能直接用的部分 vs 需要修改的部分 vs 需要重写的部分
3. **组装测试**：把各个模块组装起来，做集成测试
4. **自研填补**：只有 GitHub 上没有的部分，才从零开发

**输出格式：**

`
## 开发策略

### 可复用模块
| 模块 | GitHub 来源 | 复用度 | 需要修改的内容 |
|------|------------|--------|---------------|

### 自研模块清单
[必须从零开发的模块]
`

### Phase 6：部署反推

**从正向的部署流程出发，反向推出每个部署动作、注意事项和维护方式。**

1. **正向部署流程**：代码写完 → 构建 → 测试 → 部署到测试环境 → 验收 → 部署到生产
2. **反向推导**：为了让正向部署顺利，前置需要准备什么？
3. **注意事项**：每个部署环节最容易踩什么坑？
4. **维护方式**：上线后怎么监控？怎么回滚？怎么扩容？

**输出格式：**

`
## 部署方案

### 正向部署流程
构建 → 测试环境部署 → E2E测试 → 生产环境部署 → 监控配置

### 反向推导的前置准备
[为了上述流程顺畅，需要提前做的事]

### 注意事项
[每个环节的风险和规避方案]

### 运维维护
[监控、告警、回滚、扩容策略]
`

### Phase 7：优化与交付

1. **性能优化**：加载速度、响应时间、资源占用
2. **SEO/可发现性**：如果是面向用户的产品
3. **文档交付**：给用户的使用文档 + 给维护者的技术文档
4. **复盘检查**：对照最初的"用户旅程"，检查每个触点是否达标

## 量化任务地图（反向量化）

这是整个流程的核心产出物。**从任务模型出发，反向推导出每一个具体的动作。**

### 任务结构模板

`markdown
### Task [N]: [动词开头的简短标题]

**描述：** 一句话说明这个任务完成什么

**文件：**
- src/path/to/file.ts（新建）
- src/path/to/existing.ts（修改 L10-30）

**验收标准：**
- [ ] [具体、可测试的条件 1]
- [ ] [具体、可测试的条件 2]

**验证：**
- 测试：[具体测试命令或方式]
- 构建：[如何确认构建成功]
- 手动：[需要检查什么]

**时间：** [X] 小时 | **优先级：** P0/P1/P2 | **依赖：** Task [N]
`

### 量化规则

1. **动词开头**：每个任务必须是动作
   - ❌ "用户登录功能"
   - ✅ "设计用户登录接口"、"实现登录验证逻辑"

2. **验收标准**：每个任务 1-3 条可测试条件

3. **验证步骤**：测试 + 构建 + 手动三层验证

4. **粒度控制**：
   - 理想粒度：2-4 小时独立完成
   - 超过 8 小时必须拆分
   - 少于 30 分钟考虑合并

5. **拆分启发式（满足任一条件必须拆分）**：
   - 预估超过 2 小时 → 拆
   - 验收标准超过 3 条 → 拆
   - 涉及两个以上独立子系统 → 拆
   - 任务标题中包含"和/&/with" → 拆成两个

6. **文件级约束**：每任务涉及修改文件不超过 5 个

7. **垂直切片原则**：禁止水平切片，每个任务必须是完整功能路径
   - ❌ "设计数据库表"、"设计 API 接口"、"设计前端页面"
   - ✅ "实现用户注册功能（数据库表+API+表单页面）"

8. **排序规则**：
   - 基础先行：基础设施类任务优先
   - 高风险前置：最容易出问题的任务放在前面（fail fast）
   - 依赖满足：确保前置任务已完成

### 任务地图汇总表

`
## 量化任务地图

| # | 动作 | 验收标准 | 文件数 | 时间(h) | 优先级 | 依赖 |
|---|------|----------|--------|---------|--------|------|
| 1 | 设计用户登录接口 | API文档含≥3端点+请求响应示例 | 1 | 2 | P0 | 无 |
| 2 | 实现登录验证逻辑 | JWT服务可运行，含登录/注册/刷新 | 3 | 4 | P0 | #1 |
`

### Checkpoint 机制

每 2-3 个任务设置一个检查点：

`markdown
### Checkpoint: 完成任务 [N-M]
- [ ] 所有测试通过
- [ ] 构建成功无报错
- [ ] 核心流程端到端可跑通
- [ ] 人工审查确认
`

## 自检清单（自动生成，不可跳过）

在输出量化任务地图后，**必须**执行以下自检。每一项都必须打勾，有任何一项未通过，必须修正后再输出：

`markdown
## 自检清单

- [ ] 每个任务都以动词开头（没有名词开头的任务）
- [ ] 每个任务都有 1-3 条验收标准
- [ ] 每个任务都有验证步骤（测试/构建/手动）
- [ ] 没有任务涉及超过 5 个文件
- [ ] 没有水平切片（每个任务都是完整功能路径）
- [ ] 所有任务之间有 Checkpoint（每 2-3 个任务一个）
- [ ] 高风险任务已前置（技术选型/架构设计在最前面）
- [ ] 依赖关系正确（没有循环依赖）
- [ ] 没有任务标题中包含"和/&/with"（已拆分为两个任务）
- [ ] 总工时估算合理（与复杂度匹配）
- [ ] 简化模式下跳过了不必要的 Phase
`

**如果自检有任何一项未通过，输出修正后的版本，不要跳过。**

## 复盘模板（执行完毕后由用户填写）

量化报告不是终点。任务执行完毕后，由用户或执行者用以下模板复盘：

`markdown
## 复盘报告

### 实际耗时 vs 计划耗时
| 任务 | 计划(h) | 实际(h) | 偏差 | 原因 |
|------|---------|---------|------|------|
| #1 | 4 | 3 | -25% | 比预期顺利 |
| #2 | 6 | 9 | +50% | 遇到意料外的技术难点 |

### 低估/高估分析
- 被低估的任务：[列出+原因]
- 被高估的任务：[列出+原因]

### 遗漏的依赖关系
[执行过程中才发现的依赖]

### 经验沉淀
[下次同类任务可以改进什么]
`

# 注意事项

1. **用户视角永远是起点**：不要一上来就想技术，先想用户怎么用
2. **设计先于调研**：没有设计方案的调研是盲目的，调研的本质是纠错
3. **复用先于创造**：GitHub 上有的就别自己写，基于相似模块调整
4. **部署反推前置**：正向部署流程决定逆向准备工作
5. **规划就是任务本身**：没有计划的实现只是打字
6. **显式任务胜过隐式理解**：写下来的任务会暴露隐藏的依赖
7. **允许迭代**：第一版不可能完美，执行中根据实际情况调整
8. **不要过度量化**：简单任务不需要拆成 20 个子任务
9. **自适应模式**：简单需求用简化模式，复杂需求用完整模式，不要杀鸡用牛刀
10. **执行后必须复盘**：量化报告是起点，复盘才是闭环
