# task-quantify：任务量化 Skill

> 不做简单的任务清单。从用户怎么用出发，反推出产品需要什么，再反推出怎么开发，最后生成可执行的任务地图。

`task-quantify` 是一个 Claude Code Skill，输入一个模糊的需求即可输出一份**可执行的任务量化报告**——每个任务都是动词开头、有验收标准、有验证步骤、有优先级和依赖。自动判断复杂度，自适应选择简化/完整模式。

## 核心哲学

| 原则 | 含义 |
|------|------|
| **用户视角是起点** | 不先想技术，先从用户怎么用出发 |
| **设计先于调研** | 没有设计方案的调研是盲目的，调研的本质是纠错 |
| **复用先于创造** | GitHub 上有的就别自己写，基于相似模块调整修改，改不动的才自研 |
| **部署反推前置** | 正向部署流程决定逆向准备工作 |
| **规划就是任务本身** | 没有计划的实现只是打字 |
| **显式胜于隐式** | 写下来的任务会暴露隐藏的依赖 |

## 自适应模式系统

### 判定逻辑

```
输入需求
    │
    ├── 用户说了"简单列一下"？ ──────────────→ 简化模式
    │
    ├── 用户说了"详细拆解"？ ──────────────→ 完整模式
    │
    ├── 需求涉及 ≥2 个独立子系统？ ──────────→ 完整模式
    │
    ├── 工作量 >3 天 / 团队 >1 人？ ──────────→ 完整模式
    │
    ├── 用户没有提供任何细节？ ─────────────→ 简化模式（先追问）
    │
    └── 默认 ────────────────────────────→ 简化模式
```

### 两种模式对比

| 维度 | 简化模式 | 完整模式 |
|------|---------|---------|
| **触发条件** | 一句话能说清、单系统、≤3天 | 多系统、有依赖、>3天 |
| **Phase 执行** | Phase 1 → 量化 → Phase 7 → 自检 | Phase 1→2→3→4→5→6→7 → 量化 → 自检 → 复盘 |
| **用户旅程** | ❌ 跳过 | ✅ 详细模拟 |
| **产品设计** | ❌ 跳过 | ✅ 从旅程反推 |
| **调研纠错** | ❌ 跳过 | ✅ 竞品+技术风险 |
| **GitHub 复用** | ❌ 跳过 | ✅ 搜索→评估→组装 |
| **部署方案** | ❌ 跳过 | ✅ 正向部署→反向推导 |
| **复盘** | ❌ 跳过 | ✅ 偏差分析+经验沉淀 |
| **适用场景** | 修 bug、写页面、小功能 | 开发产品、搭建系统、大型活动 |

## 各 Phase 详解

### Phase 1：需求解析

> **不做事的阶段是最重要的阶段。** 先搞清楚到底要做什么。

| 步骤 | 说明 |
|------|------|
| **一句话复述** | 用自己的话复述，确认理解正确 |
| **维度拆解** | 对象、目标、约束、复杂度、成功标准 5 维度 |
| **领域适配** | 代码开发 / 产品设计 / 运营活动 / 研究分析 |
| **模糊澄清** | 如有模糊点，最多追问 2 个问题 |

### Phase 2：用户旅程反推（完整模式）

> 假设产品已经做好了，站在用户的角度一步步模拟——不要想技术，先想**用户**。

```
场景还原 → 第一步操作 → 核心路径 → 关键触点 → 留存钩子
    │            │           │          │          │
用户在什么      进来的       达成目标    哪个环节    什么机制让
情况下打开？   第一件事？   的最短路径   有情感波动？ 用户想回来？
```

### Phase 3：产品设计（完整模式）

> 从用户旅程的每一步，反推设计——信息架构、交互流程、核心功能（P0/P1/P2）、用户绑定机制。

### Phase 4：调研纠错（完整模式）

> **调研的本质是纠错。** 设计方案有了，调研才有靶子。

- 竞品分析：别人做对了什么、做错了什么
- 技术可行性：关键点有没有坑
- 场景验证：设计覆盖了真实场景吗
- 差异化定位：我们和别人有什么不同

### Phase 5：复用优先开发（完整模式）

> 先上 GitHub 找轮子，基于现有模块调整，改不动的再自己写。

```
GitHub 搜索 ──→ 评估复用度 ──→ 组装集成测试 ──→ 自研填补缺口
```

### Phase 6：部署反推（完整模式）

> 从最终部署状态反推每一步需要什么。

```
正向部署流程 ──→ 反向推导前置条件 ──→ 风险规避 ──→ 运维维护
```

### Phase 7：优化与交付

> 两种模式共用。性能优化、SEO、文档交付、对照"用户旅程"复查。

## 量化规则

量化任务地图是核心产出。每个任务遵守以下规则：

| # | 规则 | 示例 |
|---|------|------|
| 1 | **动词开头** | ❌ "用户登录功能" → ✅ "实现用户登录接口" |
| 2 | **验收标准 1-3 条** | ✅ "JWT token 可在 /verify 端点验证" |
| 3 | **三层验证** | 测试命令 + 构建验证 + 人工检查 |
| 4 | **粒度 2-4h** | 超 8h 必须拆分，低于 30min 考虑合并 |
| 5 | **拆分启发式** | 含"和/&/with"→拆；跨子系统→拆；超 3 条验收→拆 |
| 6 | **文件 ≤5 个** | 单任务修改文件不超过 5 个 |
| 7 | **垂直切片** | ❌ 按层切"数据库/API/前端" → ✅ 按功能切"注册（DB+API+UI）" |
| 8 | **排序优先级** | 基础先行 → 高风险前置（fail fast）→ 依赖满足 |

### 任务结构

```
### Task [N]: [动词开头的标题]
├── 描述：一句话
├── 文件：修改/新建的文件列表
├── 验收标准：[ ] 条件1  [ ] 条件2
├── 验证：测试命令 / 构建方式 / 手动检查项
├── 时间：X 小时
├── 优先级：P0/P1/P2
└── 依赖：Task [N] 或 "无"
```

### Checkpoint 机制

每 2-3 个任务之间设一个检查点：

```
### Checkpoint: 完成任务 [N-M]
- [ ] 所有测试通过
- [ ] 构建成功无报错
- [ ] 核心流程端到端可跑通
- [ ] 人工审查确认
```

## 自检与复盘闭环

### 自检清单（11 项，输出后强制执行）

在输出最终报告前，逐项核对：

```
☐ 每个任务都以动词开头
☐ 每个任务都有 1-3 条验收标准
☐ 每个任务都有验证步骤（测试/构建/手动）
☐ 没有任务涉及超过 5 个文件
☐ 没有水平切片（每个任务都是完整功能路径）
☐ 每 2-3 个任务之间有 Checkpoint
☐ 高风险任务已前置
☐ 依赖关系正确（无循环依赖）
☐ 没有任务标题含"和/&/with"
☐ 总工时估算合理
☐ 简化模式已跳过不需要的 Phase
```

**任一未通过 → 修正后重新输出。**

### 复盘闭环（完整模式）

```
执行完成
    │
    ▼
实际耗时 vs 计划耗时  ──→  偏差分析
    │
    ▼
遗漏依赖记录  ──→  经验沉淀  ──→  下次任务改进
```

## 测试

`test_cases.json` 包含 5 个测试场景，覆盖：

| ID | 场景 | 模式 | 关键验证点 |
|----|------|------|-----------|
| `simple-full-blog` | 开发个人博客系统 | 完整模式 | 含用户旅程/产品设计/竞品分析/复用策略/部署方案 |
| `simple-login-page` | 写一个登录页面 | 简化模式 | 不生成完整模式特有内容 |
| `empty-input` | 空输入 | 错误处理 | 返回错误或追问澄清 |
| `non-chinese-input` | 英文 REST API 需求 | 完整模式 | 正确处理英文输入 |
| `migration-refactor` | JWT→OAuth2 迁移 | 简化模式 | 处理重构迁移风险 |

### 测试方法

将每个 `prompt` 输入 skill，检查输出是否满足对应 `checks` 中所有 `true` 的条件。
