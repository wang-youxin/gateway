# M5 编排提示词规格

参考 `loop-prompt-maker`。M5 的产出不是"一段文字描述"，是**一份能被另一个执行者照着跑完、不需要追问的作业指导书**。

判好坏的唯一标准：

> 把这份提示词给一个完全不了解本次对话上下文的执行者，他能不能照着跑完？

---

## 5.0 先判断：这个任务到底适不适合做 Loop

**这是 M5 的第一步，之前缺了它。** 不是所有任务都该做成循环——把一次性任务包装成 loop，只会让执行者多跑几轮空转。

结论只能从这五类里选一个：

| 结论 | 含义 | 产物 |
|------|------|------|
| **适合完整 Loop** | 有明确反馈信号，可多轮修正 | 完整 Loop 脚手架 |
| **适合 Human-in-the-Loop** | 有反馈，但关键动作必须人拍板 | HITL 流程 |
| **适合 Loop-ready 结构化流程** | 结构清楚，但暂不进自动循环 | Checklist + 检查点 |
| **暂不适合 Loop** | 目标模糊、没有反馈、一次就完成 | 一次性 Prompt |
| **先做只读侦察** | 信息不够，先摸清现状 | 只读侦察 Prompt |

**没有外部反馈的任务，不进修复循环。** 只能进分析或人工确认流程——没有反馈信号的 loop，跑多少轮都是原地转。

**暂不适合时给更轻的替代**：更好的一次性 Prompt、结构化 Context、Checklist。不要硬上 loop。

---

## 5.1 选主模式（五种里选一个）

| 模式 | 适用 | 一句话 |
|------|------|--------|
| **Retry Loop** | 错误信号清楚、小步修复 | 执行→审核→改，最多 N 轮 |
| **Plan-Execute-Verify** | 目标明确、可拆解、每步可验收 | 计划→执行→验收 |
| **Explore-Narrow** | 起点模糊但有筛选标准 | 先发散后收敛 |
| **Human-in-the-Loop** | 高风险动作、价值判断 | 低风险交给 AI，拍板留给人 |
| **Lifecycle Loop** | 长期维护、周期复盘 | 每轮留状态，定期复盘 |

**必须说明两件事**：为什么选它、**为什么不是其他模式**。

> 例：数据复盘任务通常是 Explore-Narrow 不是 Retry Loop（起点模糊，没有明确错误信号可修）；发布决策通常需要 Human-in-the-Loop（不可逆）。

可以组合，但**主模式只能有一个**。

---

## 5.2 选产物档位（六档，默认最轻）

不要默认上最重的。先判断任务形态：

| 任务形态 | 产物 |
|---------|------|
| 一次就能完成 | 一次性 loop 提示词（Prompt） |
| 反馈靠人工判断 | Checklist / 人工验收表 |
| 关键动作必须人确认 | Human-in-the-Loop 流程 |
| 有明确反馈、可多轮修正 | 完整 Loop 脚手架（TODO.md + Planner/Maker/Checker/Evaluator） |
| 同一业务反复跑 | 专用 Loop Agent 包 |
| 跨项目复用 | 专用 Skill |

**必须说明"为什么不选更重的产物"。** 用户也要求更重的档位时，先说明代价，再按他说的做。

**代价按同一判据写**（见 `module-3-thinking.md` 的「问题 2.5」）：说**会不会中断周期**，不说不适感。
- ❌ "完整 Loop 脚手架配置起来麻烦""前期跑不通会挫败"
- ✅ "这条链路上没有可观察的反馈信号 → loop 跑到第 N 轮也拿不到收敛依据 → 整个循环会空转"（链条断点）
- ✅ "Agent 包会固化参数，需求一变就得重配"（锁定/二次返工）

Gateway 的 M5 **默认档位是「完整 Loop 脚手架」或更低**——因为 M4 已经把动作拆到 2-4 小时粒度，通常不需要 Agent 包。

## 5.3 决策依赖 Gate

生成提示词前，列出本轮要做的关键判断，以及每个判断依赖什么证据。

| 本轮关键判断 | 需要的证据 | 有没有 | 处理 |
|-------------|-----------|--------|------|
| 适不适合 Loop | 反馈信号是否可观察 | 有/无 | 继续 / 降级为一次性 Prompt |
| 选哪种模式 | 错误信号清晰度、目标可拆性 | ... | ... |
| 最大轮次 | 复杂度、反馈成本、回滚性、预算 | ... | ... |
| 用哪些 Skill | 本地索引里有什么 | ... | ... |

**缺证据就标注"未基于 X 校准"**，不要假装校准过。这跟 M6 的证据标准是一套东西——查不出证据就是没验证，不是大概对。

最大轮次**必须由复杂度/反馈成本/风险/回滚性/预算推导**，不能用场景默认值。

---

## 5.4 注入 Skill 能力池

读 `~/.workbuddy/skills/gateway/index.json`，筛出本次用得上的：

1. 按 `category` 粗筛
2. 按 `subtype` 收敛（dev 桶几十个，必须砍）
3. 按 `keywords`（含中文同义词）+ `capabilities` 精筛
4. 选出 3-10 个，写进"可用工具"章节

**每个 Skill 写清：名字、能干什么、什么时候该用。** 只写名字等于没写。
**路径要验过存在**——写了不存在的 Skill，Agent 执行时会卡住。

## 5.5 提示词七件套 + 三件套

### ① 任务目标与非目标

```markdown
## 目标
{一句话，结果态}

## 不做什么（非目标）
{明确排除，防止范围膨胀}
```

非目标这一栏别省。没有边界的目标会让 Agent 无限扩展。

### ② 角色表（标准四角色）

| 角色 | 干什么 | 输入 | 输出 | 可用 Skill | **不能做** |
|------|-------|------|------|-----------|-----------|
| **Planner** | 拆计划、定顺序、分配 | 任务书 | 计划 + TODO | — | 不下场干活 |
| **Maker** | 按计划产出 | 计划条目 | 产物文件 | {Skill 池} | 不改计划、不自判合格 |
| **Checker** | 逐条验闸门，判 PASS/FAIL | Maker 产物 | 判定 + 问题清单 | — | 不自己改写 |
| **Evaluator** | 整体判断有没有改善、要不要继续 | 全部 | 继续/停止/上报 | — | 不修改任何产物 |

3 个以内的简单任务可以合并角色，但 **Maker 和 Checker 必须分开**——自己做的自己验，等于没验。

**"不能做"这一列别省。** Agent 越界是协作崩掉的头号原因。

### ③ 调度与循环

```markdown
## 调度

第 0 轮：Planner 下发计划
第 1 轮：Maker 执行（可并行：动作 1 ∥ 动作 2）
第 2 轮：Checker 验闸门
第 3 轮：Evaluator 判 → 通过则交付 / 不通过则回第 1 轮

## 循环
- 循环体：Maker → Checker → Evaluator
- 继续条件：闸门未全过 且 有改善
- 退出条件：闸门全过 / 达到最大轮次 N / 连续 2 轮无改善 / 触发断路器
- 最大轮次：N（由复杂度+反馈成本+风险+回滚性推导，推导过程写出来）
```

### ④ 交接协议

```markdown
## 交接

**产物目录**：{绝对路径}/
**文件命名**：{角色}-{轮次}-{产物}.md
**状态文件**：TODO.md（每轮更新）

**每个角色收工必须写**：
- 产出了什么（文件路径）
- 遇到什么意外
- 对下游的提醒

**下游只读上游落盘的文件，不读上游的对话。** 对话会丢，文件不会。
```

### ⑤ 质量闸门

每个关键产出配一条，**可判真假**：

```markdown
| 产出 | 闸门 | 不过怎么办 |
|------|------|-----------|
| data.md | 至少 N 条记录，每条带来源 | 回 Maker 补采，最多 2 轮 |
| analysis.md | 每条结论能追溯到 data.md 的具体条目 | 回 Maker 重写 |
```

❌ "内容质量高"　✅ "每条结论后面能标出数据来源的行号，标不出的删除"

### ⑥ 断路器与失败处理

```markdown
## 断路器（触发即停机上报）
- 达到最大轮次 N
- 连续 2 轮无改善
- 越界动作（改了不该改的）
- 成本或权限风险

## 失败处理
- Agent 卡住 → 记录卡点，跳过该子项继续其他，最后上报
- 闸门 N 轮不过 → 停循环，把当前最好版本 + 未通过清单交给人类
- **前提假设错了 → 立即停机上报，不要带着错的前提继续跑**
- **需要人类决策 → 停下来问，不要自己替人类决定**
- 用户要求越过人工确认节点 → 拒绝，给一个可审计的替代流程
```

### ⑦ 终止条件

```markdown
## 终止条件
- 全部满足即停机：{可判真假的条件}
- 立即停机并上报人类：{条件}
```

### ⑧ 禁止动作清单（新增）

```markdown
## 禁止动作
- {明确列出绝对不能碰的东西}
```

**不可逆动作必须留人工确认**：merge、发布、生产配置、权限变更、支付、数据删除、商业上架、公开发布。

### ⑨ 最小 Loop 设计卡（新增）

一张表说清整个 loop：

```markdown
| 字段 | 内容 |
|------|------|
| 目标 | |
| 状态位置 | |
| 执行者 | |
| 验收者 | |
| 反馈信号 | |
| 停止规则 | |
| 人工确认节点 | |
| 禁止动作 | |
```

### ⑩ 动作清单（来自 M4）

原样继承 M4 的输出，**不许缩水**。M4 给了 6 条，M5 只能有 6 条或更多，不能变成 2 条泛化任务。

## 5.8 交付

写到 `{cwd}/.workbuddy/gateway/<slug>/agent-prompt.md`，然后给用户：

```
提示词写好了：{绝对路径}

{3-5 行摘要：什么模式、几个角色、loop 几轮、终止条件、为什么不是更重的产物}

看一眼有没有问题。确认后我可以直接按这个跑，也可以你自己拿去别的会话用。
```

**确认的判定要严格**：用户说"确认""按这个生成""可以"才算确认。用户补充信息、说"这里改一下""继续补充"只算补上下文，不算确认——别看到用户回了话就开始跑。

确认后问"现在就跑吗？"：
- 跑 → 按角色表派 Agent，串行/并行按调度图，收工按交接协议落盘，闸门不过按失败处理走
- 不跑 → 结束，文件留着

**收尾给一句 Skill 化建议**：这套流程值不值得沉淀成独立 Skill？值得就说建议名称和依据，用户确认后再建，不自动创建。

## 5.9 执行前长度检查与分段执行（2026-10-22 增补）

用户确认「跑」之后、派 Agent 之前，执行方先对 `agent-prompt.md` 做一次长度/可执行性检查：

| 检查结论 | 执行方式 |
|---------|---------|
| **不长**：能原封不动执行、基本不漏步骤 | 原样直接跑 |
| **太长**：原样跑会跳步 / 敷衍 / 做得快不做细 | 分段分步执行，每段确认后再放下一段 |

**长度是功能判据，不数 token**：界线是「能不能原封不动执行且基本不漏」。漏一步的代价远高于分段成本，拿不准就分段。

分段约定：

1. 段界按提示词自身结构切（目标 / 角色 / 调度 / 闸门 / 动作清单），不按字数平均切
2. 每段跑完对照该段验收项确认，再进下一段
3. 分段只改执行节奏，**十件套一条不许少**
4. 分段进度写进 `{slug}/state.md`，中断按段续跑
