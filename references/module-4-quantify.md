# M4 量化细则

参考 `task-quantify`（用户反推 → 设计 → 调研纠错 → 复用 → 部署反推 → 优化 → 复盘）。原技能是产品开发导向，**Gateway 要通用化**——目的可能是做生意、做内容、学东西，不一定是写代码。

| 原版（产品开发） | Gateway 通用化 |
|-----------------|---------------|
| 用户旅程反推 | **成果使用路径反推**：做出来的东西谁用、怎么用、在哪一步会失败 |
| 产品设计（信息架构/交互） | **成果形态定义**：MVP 必须有什么（P0/P1/P2） |
| 调研纠错 | 已由 M2 承担（联网对标），M4 只做纠错后的取舍 |
| 复用优先开发（GitHub 找模块） | **现成的优先**：工具/模板/平台/Skill，有就别自己造 |
| 部署反推 | **落地反推**：交付/上线/使用前要准备什么 |
| 文件级约束 ≤5 | 仅开发类任务适用 |
| 测试/构建/手动三层验证 | **验证三层**：怎么证明做完了（对非开发类同样适用） |

---

## 4.0 自适应模式

别对简单需求上全套。

| 模式 | 触发条件 | 执行 |
|------|---------|------|
| **简化** | 一句话说清、单一系统、≤3 天工作量、无跨领域依赖 | 需求理解 → 动作清单 → 自检 |
| **完整** | 多系统、有依赖、>3 天、跨领域 | 加做 成果路径反推 → 成果形态定义 → 落地反推 |

判断规则：
- 用户没给任何细节 → 简化
- 涉及 ≥2 个独立子系统/领域 → 完整
- 用户说"详细拆解" → 完整
- 用户说"简单列一下" → 简化

---

## 4.1 完整模式加做的三步

### 成果使用路径反推

**假设东西已经做好了，站在用它的人的角度，一步一步想他怎么用。**

不要先想技术、想架构、想流程——先想**谁用、怎么用**。

```
## 成果使用路径

使用场景：[什么情况下会被用上]

步骤1: [接触到] → 期望：[...] → 要点：[...]
步骤2: [核心操作] → 期望：[...] → 要点：[...]
步骤3: [拿到结果] → 期望：[...] → 要点：[...]

失败风险点：[在哪一步会掉链子]
```

**失败风险点是这一步的核心产出。** 它直接决定后面动作清单的优先级——最容易掉链子的环节，动作要前置。

### 成果形态定义（MVP 分级）

- **P0 必须有**：缺了就不算跑通
- **P1 应该有**：影响体验不影响闭环
- **P2 可以有**：锦上添花

**M4 只量化 P0 + 少量 P1。** P2 不进动作清单——用户的资源通常不够，列出 P2 只会稀释注意力。

### 落地反推

从"交付/上线/使用"这个终点往回推：

```
正向流程：做完 → 检查 → 交付 → 被使用 → 拿到反馈
反向准备：为了让上述流程顺畅，提前要做什么？
易踩的坑：每个环节最容易出什么问题？
```

## 4.2 量化规则（硬）

### 任务结构

```
### 动作 N：[动词开头的简短标题]

**描述**：一句话说明这个动作完成什么

**验收标准**：
- [ ] [可测试的条件 1]
- [ ] [可测试的条件 2]

**验证**：
- 自动：[命令 / 可跑的检查]
- 人工：[要核对什么]
- 结果：[做完之后能观察到什么变化]

**时间**：X 小时 ｜ **优先级**：P0/P1 ｜ **依赖**：动作 N
```

**验证三层是 M4 的关键补充。** 只写验收标准不写验证方式，等于给了目标不给量尺——执行者不知道怎么确认自己做完了。

| 层 | 问什么 | 非开发类例子 |
|----|-------|-------------|
| 自动 | 有没有可跑的检查 | 表格公式能不能算出数 |
| 人工 | 要核对什么 | 10 家报价是不是都记了单位和日期 |
| 结果 | 做完能观察到什么 | 手上有了可比价的一张表 |

### 八条硬规则

1. **动词开头**
   - ❌ "价格体系"　✅ "列出周边 10 家回收站收货价"

2. **验收标准 1-3 条**，可判真假
   - ❌ "价格合理"　✅ "表里能算出单件毛利"

3. **验证三层齐全**（自动 / 人工 / 结果）

4. **粒度**：理想 2-4 小时；超过 8 小时必须拆；少于 30 分钟考虑合并

5. **拆分启发式（满足任一必拆）**
   - 预估 > 2 小时
   - 验收标准 > 3 条
   - 涉及 2 个以上独立子系统/领域
   - **标题里含「和 / & / with」** ← 最容易漏的一条

6. **文件级约束**（仅开发类）：单动作涉及文件 ≤5 个

7. **垂直切片，禁止水平切片**
   - ❌ "设计数据库表"、"设计 API"、"设计前端页面"（三个都是切片，哪个都不能独立交付）
   - ✅ "实现用户注册功能（表 + 接口 + 表单）"（一条完整路径）
   - 通用领域同理：❌ "调研市场"、"调研竞品"、"调研价格" → ✅ "跑通一次完整收货报价流程"

8. **排序规则**
   - 基础先行
   - **高风险前置（fail fast）**——最容易翻车的放前面，别攒到最后
   - 依赖满足

### Checkpoint

每 2-3 个动作设一个检查点：

```
### Checkpoint：完成动作 N-M
- [ ] 所有验收标准通过
- [ ] 核心路径端到端跑得通
- [ ] 没有累积未处理的问题
```

**Checkpoint 的价值**：防止做完 8 个动作才发现第 2 个就跑偏了。

## 4.3 动作清单汇总表

```
| # | 动作 | 验收标准 | 时间(h) | 优先级 | 依赖 | 并行 |
|---|------|---------|---------|--------|------|------|
| 1 | ... | ... | 2 | P0 | 无 | 可与 2 并行 |
```

超过 8 条 → 分组，第一组标为"第一轮"，并突出**第一步**。

## 4.4 自检清单（闸门 4，不可跳过）

- [ ] 每个动作动词开头
- [ ] 每个动作 1-3 条验收标准
- [ ] 每个动作有验证三层（自动/人工/结果）
- [ ] **没有标题含「和/&/with」的动作**
- [ ] **没有水平切片**（每个动作都是完整路径）
- [ ] 粒度合规（2-4h，>8h 已拆，<30min 已合并）
- [ ] **高风险动作已前置**
- [ ] 依赖无环
- [ ] 每 2-3 个动作有 Checkpoint
- [ ] 每个动作能追溯到 M1 的目的（没有凭空多出来的）
- [ ] 完整模式没跳过该做的三步；简化模式没做多余的

**有任何一项不过，修正后再输出，不许跳过。**

## 4.5 复盘模板（执行后）

量化清单不是终点。跑完一轮回来填：

```
## 复盘

### 计划 vs 实际
| 动作 | 计划(h) | 实际(h) | 偏差 | 原因 |

### 低估/高估分析
- 被低估：...（下次同类动作乘多少系数）
- 被高估：...

### 执行中才发现的依赖
...

### 经验沉淀
...
```

复盘结果回写 `state.md`，下次同类管道直接调系数。这是管道越用越准的唯一途径。
