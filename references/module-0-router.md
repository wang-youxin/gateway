# M0 入口判别细则

Gateway 被触发后的第一个动作。判错了后面全白跑，所以这一步值得花 10 秒。

---

## 判别的核心问题

不是"用户说了什么关键词"，是：

> **用户要的是一个结果，还是一个动作？**

| | 结果（走管道） | 动作（走导航仪） |
|---|---|---|
| 形态 | 一个状态、一个局面、一个东西做出来 | 一次操作、一次转换、一次回答 |
| 能不能一步做完 | 不能，要多步 | 能，一步到位 |
| 有没有"现状"这回事 | 有，用户现在不在这个状态 | 没有，跟用户处境无关 |
| 失败了是什么样 | 没达成目的 | 这个操作没执行 |

---

## 判别信号表

### 走管道的信号

- "我想做…" "我要搞一个…" "帮我搭…" "我想从 X 变成 Y"
- 出现处境描述："我现在是…" "我手上只有…" "我已经试过…"
- 出现约束："我只有两周" "预算 5000" "就我一个人" "不懂代码"
- 出现不确定："不知道该怎么做" "不知道从哪开始" "不知道该用哪个"
- 出现目标态："做到能接单" "跑通第一单" "月入过万"

### 走导航仪的信号

- 明确的文件操作："把这个 pdf 转成 docx" "这个表格加一列"
- 明确的单点问答："这段代码为什么报错" "这篇文章讲什么"
- 点名工具/格式："用 python 写个脚本" "排版成公众号格式"
- 只涉及手上已有的东西，不涉及用户的处境和目标

### 灰色地带的处理

| 情况 | 判断 | 走向 |
|------|------|------|
| "帮我做个报价表" | 动作还是结果？看有没有现状约束。有 → 管道；没有 → 导航仪（表格类 skill） | 拿不准就问一句 |
| "我想做抖音" | 结果态，但信息几乎全空 | 管道，M2 会补维度 |
| "帮我规划一下…" | 结果态 | 管道 |
| "这个怎么做" | 看"这个"指什么。指一个动作 → 导航仪；指一个项目 → 管道 | 拿不准走管道 |
| "我不知道自己要什么" | 目的都没成型 | 管道，但 M1 输出后先帮他把问题问清楚再往下 |

**拿不准一律走管道。** 管道在 M1 解析时会发现"这其实是个单点动作"，那时退回导航仪成本很低；反过来，把多步项目当成单点动作指个 Skill 给用户，用户跑一半发现不对，成本很高。

---

## trivial 闸门（2026-10-22 增补）

「有目的」不等于「值得跑管道」。M0 判出目的后先过这道闸门——满足任一条即判 trivial，直接走导航仪，不进 M1：

1. **一句话能答完**——不需要拆解、不需要对标、不需要论证成立性
2. **有现成 skill 直指**——索引里某个 Skill 的描述/触发词直接对上，一个动作就能完成
3. **单步可达且动作 ≤3 条**——M1 复杂度会判「单步可达」的那种

为什么设这道闸门：Gateway 是高频入口，轻请求全走 M1–M5 是拿大炮打蚊子；trivial 需求走导航仪指个路，用户几十秒拿到结果。

容错方向：拿不准仍走管道。漏判 trivial 只浪费一轮管道；误判 trivial 会把真需要拆的需求当成单点动作指个 Skill 打发掉，用户跑一半发现不对，成本高得多。

---

## 用户明确点名时

用户说 `/dbs-diagnosis`、`用 jfp-roi-calculator` 这类明确指令时：

- **不拦截、不重新规划、不走管道。** 直接执行用户点名的 Skill。
- 例外：用户点名的 Skill 明显跟需求不匹配（比如点名算 ROI 但根本没数据）—— 提示一句，然后按用户说的做。不要自作主张换。

---

## 续跑识别

用户可能不是第一次进来。先看 `{cwd}/.workbuddy/gateway/*/state.md` 有没有未完成的管道。

| 用户说 | 处理 |
|--------|------|
| "继续" "下一步" "接着做" | 读 state.md，从断点继续 |
| "做完了" "搞定了" | 标记当前模块完成，进入下一模块 |
| "卡住了" "这个不行" | 定位卡在哪个模块，重新评估 |
| "换个方向" | 回 M1，保留仍有效的信息 |

有 state.md 且用户的话跟里面的目的相关 → 默认续跑，不要当成新需求重新解析。

## 输出

判别完给一句话说明走向，不要解释推理过程：

- 走管道：`这个得拆开做，我先理一下你的目的和现状。` → M1
- 走导航仪：`这个直接有现成的：` + Skill 路径和用法
