# 导航仪路径：Skill 索引匹配

当 M0 判定需求是**单一动作指向**时走这条道：查索引 → 匹配 → 指路 / 搜索 / 现造。

---

## 索引文件

**每次匹配都必须读** `~/.workbuddy/skills/gateway/index.json`。不缓存、不靠记忆、不跳过。

- 重建：`node ~/.workbuddy/skills/gateway/refresh-index.js`
- 检查：`node ~/.workbuddy/skills/gateway/refresh-index.js --check`
- 同步：`cp ~/.workbuddy/skills/gateway/index.json ~/.agents/skills/gateway/index.json`
- 索引不存在或损坏 → 先重建再匹配

schema v2.1 每条目字段：`name / description / trigger / category / subtype / capabilities / dependencies / keywords / path / group / solves_small`；顶层另有 `groups`（大类 → 解决什么问题 → 成员数）

---

## 收敛层次（0 → 0.5 → 1 → 2 → 3）

### 第 0 层：副作用过滤（安全闸门，先跑）

**会改动外部状态的 Skill 不参与自动评分匹配。** 索引里 `disable-model-invocation: true`（或 `modelInvocation: false`）的条目——带写、删、发布、推送、权限变更副作用的（如 `dbs-save`、`dbs-update`、`release-skills`、`baoyu-post-to-wechat`、`wechat-publish-pipeline`）——**直接踢出候选池**。

理由：匹配是概率行为，评分 8/8 也只是"看起来像"。把一个会发布文章的 Skill 因为"看起来像"就自动派出去，用户还没确认东西就发出去了。这类动作的触发权必须留在用户手里。

**唯一的放行条件**：用户在需求里**明确点名**了那个动作（说"保存""更新""发布""推送"且指向具体 Skill）。这时不给评分，直接给路径。

| 判定 | 处理 |
|------|------|
| 有副作用 + 用户没点名 | 踢出候选池，不出现在推荐里 |
| 有副作用 + 用户点名 | 跳过评分，直接给路径，但**执行前复述一遍将要发生什么** |
| 无副作用 | 进第 1 层正常评分 |

### 第 0.5 层：大类定位（先定大类，再谈匹配）

索引顶层 `groups` 把全部 Skill 分成若干**大类**，每个大类带三样东西：`name`（类名）、`solves`（解决什么问题）、`hints`（检索提示词）。导航第一步不是捞 Skill，是定大类：

1. 读 `groups`，按用户需求选 1 个大类——语义 reader 对 `name + solves`，机械匹配对 `hints`
2. 大类内每个 Skill 带 `solves_small`（它解决这个大类下的什么小问题），先扫这层缩小到 2-5 个候选
3. 候选仍超过 5 个，再进第 1 层用 subtype 砍

**匹配纪律：大类只按 `name + solves + hints` 判，不许堆成员关键词计分。** 24 个成员的大类会靠关键词体量抢走一切 query（实测：「代码 review」被 content-growth 抢走），大类越大偏差越狠。

大类定错比选错 Skill 更致命——后面全层都白跑。需求横跨两个大类（如「写篇文章发到公众号」横跨 writing-craft 和 wechat-publishing）→ 按主目的选一个，另一个在推荐里带一句。

新装入的 skill 若落入 `other`（未归类）组，先给它补 GROUP_RULES 再匹配——`other` 是提醒，不是常态桶。

### 第 1 层：category + subtype 过滤

| subtype | 适用场景 |
|---------|---------|
| `eng-workflow` | 工程流程/方法论：拷问、规约、TDD、评审、诊断、领域建模 |
| `dev-tool` / `devops` / `dev-generic` | 具体开发工具/脚手架/流水线 |
| `writing` | 写作与内容 |
| `visual` | 视觉生成、配图、图表 |
| `business` | 商业诊断、账号 IP |
| `publishing` | 发布、草稿箱 |
| `utility` | 翻译、音频、读图 |
| `video` | 视频、字幕 |

先用 subtype 把几十个桶砍到几个，再往下走。

### 第 2 层：capability 级匹配

匹配到具体 capability，不只是 Skill 名。一个 Skill 常常只用它的一个能力模块。

### 第 3 层：交叉评分（满分 8）

| 项 | 分值 |
|---|------|
| 领域对齐 | 0-2 |
| 类型对齐 | 0-2 |
| 对象对齐 | 0-2 |
| 约束兼容 | 0-2 |

**中文回退规则**：用户 query 为中文时，优先用 `keywords` 里的中文词命中。命中 ≥2 个中文词，对象对齐直接给 2，不强求英文术语对应。中文词为空的老 Skill 才回退到英文 token + 内容原文比对。

| 总分 | 结论 |
|------|------|
| ≥6 | 精确匹配 → 直接给路径 |
| 4-5 | 候选匹配 → 列 2-3 个 + 推荐，让用户选 |
| 0-3 | 无匹配 → 搜索生态 |

**多个候选同分是常态**（关键词袋召回的正常结果，别当成故障）。破平顺序：① `solves_small` 与 query 主词的语义接近度（"写口播稿" ≈ "口播脚本生成器"，字面重合度帮不上忙）；② 仍平就并列展示带推荐，让用户选——**不许硬指定一个**。

**候选必须带推荐**，不能只列选项让用户自己挑。

## 输出

```
## 路径

→ {skill-name} / {capability}
→ 理由：领域✅ 类型✅ 对象✅ 约束✅ (8/8)

用法：{怎么用，一句话}
完成后回来告诉我，或者直接 /gateway 继续。
```

模糊匹配时：

```
候选：
  1. ⭐ {skill-A} (7/8) — {为什么最匹配}
  2. {skill-B} (6/8) — {适合什么情况}

不确定就选 1，用错了随时回来换。
```

## 无匹配时：搜索生态（两个源都要查）

**`find-skills` 和 `findskills` 是两个不同生态的搜索源，不是同一个东西。** 只查一个会漏掉一半。

| 源 | 生态 | 特点 |
|---|------|------|
| `find-skills` | skills.sh / `npx skills` | 英文为主，可查安装数 |
| `findskills` | ClawHub / OpenClaw | 中英双语，中文命中更好 |

两个源都跑，关键词构造：

- 用 M1 提取的领域 + 类型构造关键词，**英文 + 中文各一组**
- 至少 2 组不同关键词，两个源各查一遍
- 优先 ≥1K 安装、官方来源
- 展示 top 3（合并去重后），给质量评估

| 结果 | 处理 |
|------|------|
| 找到了 | 问用户要不要装 → 装 → 刷新索引 → **双份同步** → 重新匹配 |
| ≥8 个结果 | 用约束过滤到 3 个再展示 |
| 两个源都 0 结果 | 直接进"现造"，不要让用户干等 |

**只查了一个源就下结论"生态里没有"是错的。** 要说清楚查了哪两个源、各用了什么关键词。

## 现造：调用 skill-creator

**必须先出方案，用户确认后才执行。**

```markdown
## 需要新建一个 Skill

### 为什么现有的都不行
- {原因}

### 建造方案
- 名称：{kebab-case}
- 核心能力：{做什么}
- 输入/输出：{什么进来什么出去}
- 依赖：{用到哪些已有 Skill}
- 验收方式：{怎么验证它管用}
- 复杂度：{简单/中等/复杂}

### 可复用模块
- {capability} from {skill-name}
```

方案太复杂用户不敢批 → 说明可以先做简化版只含核心能力，后面再迭代。
用户拒绝 → 给两条退路：换个思路重新出方案 / 放弃这个任务先做别的。

创建完成 → 刷新索引 → 双份同步 → 回到第 1 层重新匹配。

---

## 常见踩坑

| 坑 | 处理 |
|---|------|
| 需求太模糊提取不出领域 | 最多追 2 个问题，必须是选择题不是开放题 |
| 2-3 轮对齐不上 | 列出确定的和不确定的，按确定的先走 |
| 用户明确知道要用哪个 Skill | 不拦截，直接放行 |
| 匹配到的 Skill 路径已不存在 | 从索引移除该条，继续匹配，提示刷新索引 |
| 匹配到 Gateway 自己 | 不外派给自己，用内置逻辑处理 |
